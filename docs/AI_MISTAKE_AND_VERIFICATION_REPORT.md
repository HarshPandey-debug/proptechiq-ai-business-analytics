# Manual Verification & AI Mistake Post-Mortem Report

> **Dataset Provenance Note**: This project uses a **100% synthetic, simulated student-housing marketplace dataset ("CampusStay PBSA Marketplace")** generated programmatically by `src/generate_dataset.py`. It does not contain proprietary data from any real-world company.

## 1. Executive Summary: Manual Verification vs. AI Output

When deploying Large Language Models (LLMs) like **Gemini 2.0 Flash** for Text-to-SQL business analytics, syntactic validity does not guarantee analytical correctness. A SQL query can execute with zero database errors while silently distorting financial metrics by hundreds of percent due to **relational grain mismatches (1-to-many join fan-out)** or **status filter omissions**.

In this project, every AI-generated SQL query was audited against an independent **Python/Pandas ground-truth calculation** (`src/verify_ai_vs_ground_truth.py`) and cross-checked against `data/cleaned/data_quality_audit_report.json` with **£0.00 variance**. During testing, manual verification caught a severe **1-to-many SQL join fan-out mistake** generated by an unguarded AI prompt that overstated Platform Commission Revenue by **£4,695,733.76 (+478.37%)** and Gross Booking Value (GBV) by **£57,747,632.00 (+478.58%)**.

## 2. Documented AI Mistake: The 1-to-Many Relational Fan-Out Trap

### 2.1 The Natural Language Prompt

During initial testing of the Text-to-SQL assistant (prior to adding grain guardrails to the system prompt), the assistant was given the following multi-table business prompt:

> *"Calculate total confirmed Gross Booking Value, Platform Commission Revenue, Net Profit, and Total Collected Installment Payments by City."*

### 2.2 The Broken AI-Generated PostgreSQL Query

Because the user prompt mentioned both booking-level revenue metrics (`Gross Booking Value`, `Platform Commission Revenue`, `Net Profit`) and payment-level metrics (`Collected Installment Payments`), the unguarded LLM generated a single flat `SELECT` statement joining `bookings`, `properties`, `payment_installments`, and `property_promotions`:

```sql
-- ❌ BROKEN AI-GENERATED SQL QUERY (CAUSES 1-TO-MANY JOIN FAN-OUT)
SELECT
    p.city,
    COUNT(b.booking_id) AS ai_reported_bookings,
    ROUND(SUM(b.gross_booking_value_gbp), 2) AS ai_inflated_gbv_gbp,
    ROUND(SUM(ROUND(b.gross_booking_value_gbp * (p.partner_commission_pct / 100.0), 2)), 2) AS ai_inflated_revenue_gbp,
    ROUND(
        SUM(ROUND(b.gross_booking_value_gbp * (p.partner_commission_pct / 100.0), 2))
        - SUM(b.marketing_cpa_gbp + p.ops_servicing_cost_gbp),
        2
    ) AS ai_inflated_net_profit_gbp,
    ROUND(SUM(pi.installment_amount_gbp), 2) AS ai_inflated_payments_collected_gbp
FROM bookings b
INNER JOIN properties p
    ON b.property_id = p.property_id
LEFT JOIN payment_installments pi
    ON b.booking_id = pi.booking_id
LEFT JOIN property_promotions pr
    ON p.property_id = pr.property_id
WHERE b.booking_status = 'Confirmed'
GROUP BY p.city
ORDER BY ai_inflated_revenue_gbp DESC;
```

### 2.3 Why the AI Query Failed (Root Cause Analysis)

The query executed without syntax errors in PostgreSQL, but violated **three relational grain invariants**:

1. **Booking-to-Installment Fan-Out (`1 : N`)**: In the `bookings` table, the grain is **1 row per lease booking** (`945` confirmed rows). In `payment_installments`, students pay rent in **1, 3, or 4 installments** (`2.95` installments per booking on average). Joining `bookings` directly to `payment_installments` duplicated each booking row `N` times (`N ∈ {1, 3, 4}`), multiplying `b.gross_booking_value_gbp`, commission revenue, and direct costs by the number of installments.
2. **Property-to-Promotion Cartesian Fan-Out (`1 : M`)**: Joining `properties` directly to `property_promotions` (`1 to 3` promotional campaigns per property) created a secondary fan-out across every booking and installment row (`N × M` multiplication per booking), which also inflated `SUM(pi.installment_amount_gbp)` from **£12,066,564.00** to **£23,533,336.00**.
3. **Count Distortion (`COUNT(b.booking_id)` vs. `COUNT(DISTINCT b.booking_id)`)**: Because `COUNT(b.booking_id)` counts non-null joined rows rather than unique bookings, the AI query reported **5,625 confirmed bookings** instead of the true **945 confirmed bookings**.

## 4. How the Mistake Was Corrected

### 4.1 SQL Remediation: Pre-Aggregating via Common Table Expression (CTE)

To preserve the **1-row-per-booking** grain on `bookings`, `payment_installments` is pre-aggregated by `booking_id` inside a CTE (`booking_payments`) before joining to `bookings`, and `property_promotions` is excluded when promotional discounts are not part of the requested metric:

```sql
-- ✅ CORRECTED & VERIFIED POSTGRESQL QUERY (PRE-AGGREGATED CTE AT BOOKING GRAIN)
WITH booking_payments AS (
    SELECT
        booking_id,
        COUNT(payment_id) AS installment_count,
        ROUND(SUM(installment_amount_gbp) FILTER (WHERE payment_status = 'Paid'), 2) AS collected_payments_gbp
    FROM payment_installments
    GROUP BY booking_id
)
SELECT
    p.city,
    COUNT(b.booking_id) AS verified_confirmed_bookings,
    ROUND(SUM(b.gross_booking_value_gbp), 2) AS verified_gbv_gbp,
    ROUND(SUM(ROUND(b.gross_booking_value_gbp * (p.partner_commission_pct / 100.0), 2)), 2) AS verified_revenue_gbp,
    ROUND(
        SUM(ROUND(b.gross_booking_value_gbp * (p.partner_commission_pct / 100.0), 2))
        - SUM(b.marketing_cpa_gbp + p.ops_servicing_cost_gbp),
        2
    ) AS verified_net_profit_gbp,
    ROUND(SUM(COALESCE(bp.collected_payments_gbp, 0)), 2) AS verified_payments_collected_gbp
FROM bookings b
INNER JOIN properties p
    ON b.property_id = p.property_id
LEFT JOIN booking_payments bp
    ON b.booking_id = bp.booking_id
WHERE b.booking_status = 'Confirmed'
GROUP BY p.city
ORDER BY verified_revenue_gbp DESC;
```

### 4.2 System Prompt & Static SQL Guardrail Engineering

In `src/ai_analytics_assistant.py`, two permanent engineering safeguards were added:

1. **Explicit Grain Annotations in the Gemini System Prompt**: Annotated each table in `SCHEMA_CONTEXT` with its exact cardinality (`Grain: 1 row per lease booking` vs. `1-to-MANY per booking`) and added `Rule 3 (ANTI-FAN-OUT GUARDRAIL)` instructing Gemini to always pre-aggregate `payment_installments` inside a `WITH` CTE before joining to `bookings`.
2. **Programmatic Fan-Out Blocker (`validate_sql_safety_and_grain`)**: Before any AI-generated query executes against PostgreSQL, a static validation gate inspects the SQL string. If a query joins `payment_installments` or `property_promotions` while summing `gross_booking_value_gbp` without a `WITH` CTE, execution is blocked and a `GRAIN TRAP DETECTED` alert is raised.
